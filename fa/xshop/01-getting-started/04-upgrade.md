# راهنمای به‌روزرسانی پروژه

روش به‌روزرسانی پروژه به این بستگی دارد که آیا در کدهای اصلی تغییراتی ایجاد کرده‌اید یا خیر.

به‌طور کلی، دو نوع نصب داریم:

- **Consumer:** استفاده از پروژه بدون تغییر در کدهای اصلی.
- **Developer:** توسعه پروژه، افزودن قابلیت‌های اختصاصی یا تغییر کدهای اصلی متناسب با نیازهای یک کسب‌وکار یا مشتری.

مخزن رسمی پروژه در GitHub، مرجع اصلی دریافت نسخه‌های منتشرشده است.

## ۱. به‌روزرسانی Consumer

اگر از نسخه اصلی پروژه استفاده می‌کنید و تغییرات اختصاصی در کدهای آن نداده‌اید، می‌توانید طبق دستورالعمل نسخه جدید، پروژه را به‌روزرسانی کنید.

پیش از شروع:

- از دیتابیس و فایل‌های مهم نسخه پشتیبان تهیه کنید.
- تغییرات نسخه جدید و موارد ناسازگار احتمالی را بررسی کنید.
- دستورالعمل اختصاصی انتشار نسخه جدید را مطالعه کنید.

سپس، در صورت مطابقت با دستورالعمل انتشار، دستورات زیر را اجرا کنید:



```bash
git pull 
composer install --no-dev --optimize-autoloader
php artisan migrate --force
php artisan optimize:clear
php artisn client
pnpm build
```

**نکته:** در محیط Production معمولاً باید از `composer install` استفاده کنید تا وابستگی‌ها مطابق فایل `composer.lock` نصب شوند. اجرای `composer update` ممکن است نسخه وابستگی‌ها را تغییر دهد و روش پیش‌فرض به‌روزرسانی نیست.

ممکن است بعضی نسخه‌ها به اقدامات اضافی نیاز داشته باشند؛ بنابراین همیشه دستورالعمل همان نسخه را در اولویت قرار دهید.

## ۲. به‌روزرسانی Developer

اگر کدهای پروژه را تغییر داده‌اید یا قابلیت‌های اختصاصی به آن اضافه کرده‌اید، باید تغییرات خود را با نسخه جدید پروژه ادغام کنید.

نمونه‌هایی از سفارشی‌سازی عبارت‌اند از:

- تغییر منطق قیمت‌گذاری محصولات یا پیاده‌سازی Observerهای اختصاصی.
- افزودن ماژول‌هایی مانند ارسال پیام تبریک تولد مشتری.
- تغییر Theme پنل مدیریت یا فروشگاه.
- افزودن زبان جدید یا تغییر فایل‌های ترجمه موجود.
- تغییر مدل‌ها، کنترلرها، سرویس‌ها، Viewها یا Migrationها.
- افزودن قابلیت‌ها یا اتصال به سرویس‌های اختصاصی مشتری.

در این شرایط، اجرای ساده `git pull` لزوماً برای به‌روزرسانی کافی نیست.

### مرحله اول: ایجاد Fork

از مخزن رسمی پروژه در GitHub یک Fork ایجاد کنید و آن را Clone کنید:



```bash
git clone https://github.com/YOUR_USERNAME/PROJECT.git
cd PROJECT
```

آدرس بالا نمونه است و باید با آدرس واقعی Fork خود جایگزین شود.

### مرحله دوم: تعریف مخزن رسمی به‌عنوان Upstream

در پوشه پروژه اجرا کنید:


```bash
git remote add upstream https://github.com/4xmen/xshop.git
git remote -v
```

در این ساختار:

- `origin`: مخزن Fork شما در GitHub است.
- `upstream`: مخزن رسمی پروژه است.

### مرحله سوم: جداسازی تغییرات اختصاصی

توصیه می‌شود تغییرات اختصاصی را در Branch جداگانه نگهداری کنید و Branch `master` را برای دنبال کردن نسخه رسمی پروژه در نظر بگیرید.


برای مثال:

```text
master    # نسخه رسمی پروژه
custom    # تغییرات اختصاصی
```



**اگر تاکنون تغییرات اختصاصی خود را مستقیماً روی Branch****`master`****انجام داده‌اید، نگران نباشید؛ نیازی به شروع مجدد پروژه یا از دست دادن تغییرات نیست.** پیش از ادامه، وضعیت مخزن خود را بررسی کنید و یکی از روش‌های زیر را انتخاب کنید:

- **روش اول: ایجاد Branch جدید (پیشنهادی)**اگر `master` شما شامل تغییرات اختصاصی است و هنوز با نسخه رسمی جدید هماهنگ نشده، می‌توانید از وضعیت فعلی آن یک Branch جدید بسازید:

  ```  bash
  git switch master
  git switch -c custom
  git push -u origin custom
  ```
  با این کار، تغییرات فعلی شما در Branch `custom` نیز حفظ می‌شوند و می‌توانید از این پس توسعه اختصاصی را در آن ادامه دهید.
- **روش دوم: تغییر نام Branch**اگر `master` شما کاملاً اختصاصی شده و دیگر قصد ندارید از آن به‌عنوان شاخه دنبال‌کننده نسخه رسمی استفاده کنید، می‌توانید نام آن را به `custom` تغییر دهید:
  
  ```bash
  git branch -m master custom
  git push -u origin custom
  ```
  این روش نام Branch محلی را تغییر می‌دهد؛ اما ممکن است برای هماهنگی با تنظیمات مخزن GitHub یا سرور Production به اقدامات دیگری نیاز داشته باشید.

**نکته مهم:** این دستورات را بدون بررسی وضعیت مخزن اجرا نکنید. اگر `master` شما از قبل شامل تغییرات رسمی جدید است، یا Branch `custom` از قبل وجود دارد، ابتدا وضعیت Branchها و تغییرات را بررسی کنید. تا زمانی که از حفظ تغییرات اختصاصی خود مطمئن نشده‌اید، Branch قبلی را حذف نکنید.

تغییرات اختصاصی خود را Commit کنید و در Fork نگه دارید:


```bash
git switch -c custom
git add .
git commit -m "Add custom functionality"
git push -u origin custom
```

اگر از قبل روی پروژه تغییرات زیادی اعمال کرده‌اید، ابتدا وضعیت فعلی مخزن و تاریخچه Commitها را بررسی کنید. ایجاد Branch جدید به‌تنهایی تغییرات قبلی را تفکیک نمی‌کند.

### مرحله چهارم: دریافت نسخه رسمی جدید

پیش از به‌روزرسانی، مطمئن شوید تغییرات اختصاصی شما Commit شده‌اند و از اطلاعات مهم نسخه پشتیبان دارید.

سپس اجرا کنید:



```bash
git fetch upstream
```

Branch رسمی محلی را با آخرین نسخه منتشرشده هماهنگ کنید:



```bash
git switch master
git merge upstream/master
```

**توجه:** شاخه `master` مخزن رسمی، نسخه پایدار پروژه را دنبال می‌کند. تغییرات شاخه `dev` ممکن است هنوز نهایی و منتشر نشده باشند؛ بنابراین برای به‌روزرسانی معمول، از `upstream/master` استفاده کنید.

### مرحله پنجم: ادغام نسخه جدید با تغییرات اختصاصی

پس از به‌روزرسانی `master`، شاخه اختصاصی خود را با آن هماهنگ کنید:



```bash
git switch custom
git merge master
```

اگر Conflict وجود نداشته باشد، Git تغییرات را ادغام می‌کند.

اگر Conflict وجود داشته باشد، باید فایل‌های متداخل را بررسی کنید و مشخص کنید کدام تغییرات رسمی و اختصاصی باید حفظ یا با یکدیگر ترکیب شوند.

پس از حل Conflictها، وضعیت مخزن را بررسی کنید:



```bash
git status
```

اگر Merge هنوز تکمیل نشده است، فایل‌های حل‌شده را ثبت کنید:



```bash
git add .
git commit -m "Merge upstream updates"
```

اگر Git به‌صورت خودکار Merge را تکمیل کرده و Commit ساخته باشد، نیازی به Commit مجدد نیست.

**تا زمانی که Merge با موفقیت تکمیل نشده و مشکلات احتمالی برطرف نشده‌اند، به مرحله انتشار نروید.**

### مرحله ششم: بررسی و آزمایش

پس از ادغام تغییرات، پروژه را بررسی کنید:



```bash
composer install
php artisan test
```

در صورت نبود تست خودکار، قابلیت‌های اصلی پروژه را دستی بررسی کنید.

موارد زیر را نیز در نظر بگیرید:

- سازگاری ماژول‌ها، Observerها و Integrationهای اختصاصی.
- فایل‌های ترجمه و Themeهای سفارشی.
- تغییرات ساختار دیتابیس و Migrationهای جدید.
- تغییرات وابستگی‌ها و تنظیمات موردنیاز نسخه جدید.
- عملکرد قابلیت‌های اصلی فروشگاه، از جمله ثبت سفارش، پرداخت و مدیریت محصولات.

پیش از اجرای Migrationها در Production، از دیتابیس نسخه پشتیبان تهیه کنید و دستورالعمل نسخه جدید را بررسی کنید.

### مرحله هفتم: ارسال نسخه به‌روزشده به GitHub خودتان

پس از اطمینان از صحت ادغام و آزمایش تغییرات، Branch اختصاصی را به مخزن Fork خود ارسال کنید:



```bash
git push origin custom
```

اکنون نسخه به‌روزشده، همراه با تغییرات اختصاصی، در مخزن GitHub شما قرار دارد.

### مرحله هشتم: به‌روزرسانی سرور Production

برای انتشار نسخه جدید، به سرور Production متصل شوید و وارد پوشه پروژه شوید.

دستورات زیر با این فرض نوشته شده‌اند که سرور از قبل از مخزن Fork شما استفاده می‌کند و Branch اختصاصی آن `custom` است.

ابتدا آخرین تغییرات را دریافت کنید:



```bash
git fetch origin
```

سپس Branch اختصاصی را به‌روزرسانی کنید:



```bash
git switch custom
git pull --ff-only origin custom
```

پس از دریافت موفق کدها، وابستگی‌ها و Migrationها را مطابق دستورالعمل نسخه جدید اجرا کنید:



```bash
composer install --no-dev --optimize-autoloader
php artisan migrate --force
php artisan optimize:clear
php artisn client
pnpm build
```

در پایان، سلامت برنامه و عملکرد قابلیت‌های اصلی را بررسی کنید. در صورت نیاز، Queue Workerها، Cacheها و سایر سرویس‌های مرتبط را مطابق روش استقرار پروژه مدیریت کنید.

**مهم:** ارسال تغییرات به GitHub به‌تنهایی باعث به‌روزرسانی سرور Production نمی‌شود. پس از Push موفق، باید فرایند Deploy روی سرور نیز انجام شود.

دستورات فوق برای یک استقرار ساده مبتنی بر Git هستند. اگر پروژه شما از فرایند استقرار دیگری استفاده می‌کند، دستورات را مطابق همان فرایند تنظیم کنید.

## ۳. نکات مهم درباره سفارشی‌سازی

### تغییرات اختصاصی

تغییرات اختصاصی ممکن است با تغییرات نسخه‌های جدید تداخل داشته باشند و به بررسی یا اصلاح دستی نیاز پیدا کنند. با این حال، اگر هنگام ادغام یا به‌روزرسانی با مشکل مواجه شدید، می‌توانید از مسیر پشتیبانی پروژه برای دریافت راهنمایی کمک بگیرید.

### فایل‌های ترجمه

تغییر فایل‌های ترجمه اصلی، مانند `fa.json` یا `ar.json`، ممکن است هنگام به‌روزرسانی باعث Conflict یا از دست رفتن بخشی از تغییرات شود.

نسخه جدید پروژه ممکن است کلیدهای ترجمه جدید اضافه کند، کلیدهای قبلی را تغییر دهد یا مقادیر آن‌ها را اصلاح کند.

در صورت امکان، از فایل‌های ترجمه اختصاصی یا ساختار ترجمه جداگانه استفاده کنید تا نیاز به تغییر مستقیم فایل‌های اصلی کاهش یابد.

### Themeهای اختصاصی

در صورت تغییر Theme پنل مدیریت یا فروشگاه، تغییرات خود را تا حد امکان از Theme اصلی جدا نگه دارید.

به‌روزرسانی Viewها، کامپوننت‌ها، استایل‌ها یا فایل‌های Frontend ممکن است به اصلاح Theme اختصاصی نیاز داشته باشد.

### Migrationهای اختصاصی

Migrationهای منتشرشده هسته را پس از انتشار تغییر ندهید، مگر اینکه دستورالعمل رسمی پروژه خلاف آن را مشخص کرده باشد.

برای تغییرات اختصاصی دیتابیس، Migrationهای جداگانه بسازید و پیش از اجرای Migrationهای نسخه جدید در Production، سازگاری آن‌ها را بررسی کنید.

### توسعه قابلیت‌های جدید

برای کاهش تداخل در نسخه‌های آینده، تا حد امکان از ماژول‌های مستقل، سرویس‌ها، Observerها، Eventها و سایر Extension Pointهای موجود در پروژه استفاده کنید.

جداسازی کدهای اختصاصی از هسته پروژه، نگهداری و به‌روزرسانی نسخه‌های آینده را ساده‌تر می‌کند.

## ۴. دریافت پشتیبانی

اگر هنگام به‌روزرسانی یا ادغام تغییرات اختصاصی با نسخه جدید با مشکل مواجه شدید، می‌توانید یک Issue در مخزن رسمی پروژه ایجاد کنید.

برای بررسی دقیق‌تر، اطلاعات زیر را ارائه دهید:

- نسخه فعلی و نسخه مقصد.
- مراحل و دستورات اجراشده.
- متن کامل خطا یا جزئیات Conflict.
- شرح تغییرات اختصاصی مرتبط با مشکل.
- مراحل لازم برای بازتولید مشکل، در صورت امکان.

تیم پروژه موضوع را بررسی می‌کند و در حد امکان برای پیدا کردن راه‌حل راهنمایی خواهد کرد. به دلیل تفاوت در سفارشی‌سازی‌های هر نصب، ممکن است برخی مشکلات به بررسی و اصلاح کد اختصاصی همان نصب نیاز داشته باشند.

از ارسال رمز عبور، کلیدهای API، توکن‌های دسترسی یا سایر اطلاعات حساس خودداری کنید.

## خلاصه

- **Consumer:** به‌روزرسانی طبق دستورالعمل رسمی نسخه جدید.
- **Developer:** نگهداری تغییرات اختصاصی در Fork و Branch جداگانه.
- **دریافت نسخه جدید:** به‌روزرسانی `master` از `upstream/master` و ادغام آن در Branch اختصاصی.
- **پس از ادغام:** بررسی، آزمایش و ارسال تغییرات به GitHub خودتان.
- **انتشار نهایی:** به‌روزرسانی سرور Production از مخزن خودتان.
- **در صورت بروز مشکل:** ثبت Issue در مخزن رسمی پروژه و ارائه اطلاعات لازم برای بررسی.
