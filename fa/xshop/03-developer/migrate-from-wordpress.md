## ۱. معرفی

قابلیت `xshift` ابزاری برای انتقال اطلاعات از یک وب‌سایت مبتنی بر WordPress و WooCommerce به سیستم xShop است.

این ابزار از طریق یک افزونه اختصاصی در وردپرس، اطلاعات موردنیاز را در قالب JSON در اختیار پروژه xShop قرار می‌دهد. سپس یک دستور Artisan در Laravel اطلاعات را دریافت کرده و در پایگاه داده و فضای ذخیره‌سازی xShop ثبت می‌کند.

اطلاعاتی که در پیاده‌سازی فعلی پشتیبانی می‌شوند عبارت‌اند از:

- دسته‌بندی محصولات (Product Categories)
- گروه‌های محتوا (Groups)
- نوشته‌ها و مطالب وبلاگ (Posts)
- محصولات فروشگاه (Products)
- تصاویر دسته‌بندی‌ها
- تصاویر شاخص نوشته‌ها
- تصاویر محصولات
- تگ‌های نوشته‌ها
- اطلاعات اولیه موجودی، قیمت و SKU محصولات
- ایجاد ریدایرکت برای آدرس‌هایی که پس از مهاجرت تغییر کرده‌اند

> **نکته:** انتقال اطلاعات کاربران، سفارش‌ها، فاکتورها و سایر اطلاعات فروشگاه در کد فعلی به‌صورت عملیات مستقل پیاده‌سازی نشده است. وجود مدل‌های مربوط به این اطلاعات در کد به معنای پشتیبانی از مهاجرت آن‌ها نیست.

## ۲. پیش‌نیازها

پیش از شروع مهاجرت، موارد زیر باید بررسی شوند.

### ۲.۱. پیش‌نیازهای سایت مبدأ

- سایت WordPress باید در دسترس باشد.
- افزونه WooCommerce باید نصب و فعال باشد، اگر قصد انتقال محصولات فروشگاه را دارید.
- افزونه اختصاصی `xshift` باید نصب و فعال باشد.
- مسیر API افزونه باید از سمت پروژه xShop قابل دسترسی باشد.
- تصاویر و فایل‌های موردنیاز باید از طریق URL قابل دریافت باشند.

### ۲.۲. پیش‌نیازهای پروژه xShop

- پروژه xShop باید نصب و قابل اجرا باشد.
- تنظیمات اتصال به پایگاه داده در فایل `.env` صحیح باشد.
- وابستگی‌های PHP و Composer پروژه نصب شده باشند.
- جداول و Migrationهای موردنیاز اجرا شده باشند.
- فضای دیسک کافی برای ذخیره تصاویر وجود داشته باشد.
- کاربر اجرایی PHP به مسیرهای ذخیره‌سازی دسترسی نوشتن داشته باشد.
- حداقل یک کاربر در جدول کاربران وجود داشته باشد؛ زیرا نوشته‌ها و محصولات مهاجرت‌شده به اولین کاربر موجود در سیستم منتسب می‌شوند.

### ۲.۳. تهیه نسخه پشتیبان

قبل از اجرای مهاجرت روی محیط عملیاتی، از پایگاه داده و فایل‌های پروژه نسخه پشتیبان تهیه کنید.

به‌خصوص پیش از اجرای عملیات پاک‌سازی، از حذف اطلاعات موجود اطمینان حاصل کنید.

**پیشنهاد می‌شود اولین اجرای مهاجرت در محیط توسعه یا روی یک نسخه آزمایشی از سایت مقصد انجام شود.**

## ۳. معماری و نحوه عملکرد مهاجرت

فرآیند مهاجرت از دو بخش تشکیل شده است.

### بخش اول: افزونه وردپرس

افزونه `xshift` در پوشه `thirdparty` پروژه قرار دارد. این افزونه اطلاعات وردپرس را از طریق API اختصاصی در مسیر زیر ارائه می‌کند:


```
/wp-json/xshift/v1
```

برای مثال، اطلاعات نوشته‌ها از مسیر زیر دریافت می‌شوند:


```
https://wp.example.com/wp-json/xshift/v1/posts
```

مسیرهای مورد استفاده در کد فعلی عبارت‌اند از:

| مسیر API | اطلاعات |
| --- | --- |
| `/product-categories` | دسته‌بندی محصولات |
| `/categories` | گروه‌های محتوا |
| `/posts` | نوشته‌ها |
| `/products` | محصولات |

### بخش دوم: دستور Artisan در Laravel

دستور مهاجرت در کلاس زیر پیاده‌سازی شده است:

```
app/Console/Commands/xShift.php
```

نام دستور:


```bash
php artisan xshift
```

ساختار عمومی دستور به شکل زیر است:



```bash
php artisan xshift {action} {url?}
```

- `action`: عملیات موردنظر برای مهاجرت
- `url`: آدرس سایت WordPress مبدأ

پارامتر `url` در تعریف دستور اختیاری است، اما برای عملیات دریافت اطلاعات الزامی خواهد بود.

در هر عملیات مهاجرت، xShop اطلاعات JSON را از API وردپرس دریافت کرده و سپس رکوردهای متناظر را در پایگاه داده مقصد ایجاد می‌کند.

## ۴. نصب افزونه xshift در وردپرس

۱. وارد پنل مدیریت WordPress شوید.

۲. از بخش افزونه‌ها، گزینه افزودن افزونه جدید را انتخاب کنید.

۳. افزونه `xshift` موجود در پوشه `thirdparty` پروژه xShop را نصب کنید.

۴. افزونه را فعال کنید.

۵. آدرس API را بررسی کنید. برای مثال، اگر آدرس سایت وردپرس `http://wp.test/` باشد، مسیر API نوشته‌ها به شکل زیر خواهد بود:


```
http://wp.test/wp-json/xshift/v1/posts
```

آدرس بالا صرفاً نمونه است. آدرس واقعی سایت مبدأ را جایگزین کنید.

**نکته امنیتی:** اگر API اطلاعات سایت را بدون احراز هویت در اختیار درخواست‌کنندگان قرار می‌دهد، دسترسی به آن را متناسب با شرایط مهاجرت کنترل کنید. در محیط عملیاتی بهتر است از HTTPS استفاده شود.

## ۵. آماده‌سازی پروژه xShop

به پوشه اصلی پروژه xShop بروید:


```bash
cd /path/to/xshop
```

در صورت نیاز، وضعیت نصب وابستگی‌ها و تنظیمات پروژه را بررسی کنید:


```bash
composer install
php artisan migrate
```

دستور `php artisan migrate` را فقط مطابق رویه استقرار پروژه اجرا کنید؛ به‌ویژه اگر پایگاه داده از قبل دارای اطلاعات است.

سپس بررسی کنید که حداقل یک کاربر در سیستم وجود داشته باشد.

برای اجرای مهاجرت، آدرس سایت مبدأ را با فرمت مناسب وارد کنید:


```text
http://wp.test/
```

کد فعلی آدرس را از طریق حذف `/` ابتدا و انتها نرمال‌سازی می‌کند. در نتیجه وجود یا نبود اسلش انتهایی معمولاً تفاوتی ایجاد نمی‌کند.

## ۶. اجرای دستورات مهاجرت

### ۶.۱. مهاجرت گروه‌های محتوا



```bash
php artisan xshift group http://wp.test/
```

این دستور اطلاعات مسیر `/categories` را دریافت می‌کند و گروه‌های محتوا را در جدول مربوطه ثبت می‌کند.

اطلاعاتی که در کد فعلی منتقل می‌شوند:

- شناسه
- نام
- توضیحات
- نامک (Slug)
- شناسه گروه والد

در صورت تغییر مسیر آدرس گروه، یک ریدایرکت نیز ثبت می‌شود.

### ۶.۲. مهاجرت نوشته‌ها



```bash
php artisan xshift post http://wp.test/
```

این دستور اطلاعات نوشته‌ها را از مسیر `/posts` دریافت می‌کند.

اطلاعات منتقل‌شده شامل موارد زیر است:

- شناسه نوشته
- عنوان
- نامک
- محتوای نوشته
- خلاصه نوشته
- گروه‌های مرتبط
- تگ‌ها
- تصویر شاخص، در صورت وجود
- تاریخ ایجاد نوشته

در پیاده‌سازی فعلی، وضعیت نوشته‌ها هنگام مهاجرت روی مقدار `1` قرار می‌گیرد و نوشته‌ها به اولین کاربر موجود در سیستم منتسب می‌شوند.

### ۶.۳. مهاجرت دسته‌بندی محصولات



```bash
php artisan xshift category http://wp.test/
```

این دستور اطلاعات دسته‌بندی محصولات را از مسیر `/product-categories` دریافت می‌کند.

اطلاعات منتقل‌شده عبارت‌اند از:

- شناسه دسته‌بندی
- نام
- توضیحات
- نامک
- دسته‌بندی والد
- تصویر دسته‌بندی، در صورت وجود

تصاویر دسته‌بندی در مسیر زیر ذخیره می‌شوند:



```text
storage/app/public/categories/
```

همچنین در صورت موفقیت‌آمیز بودن پردازش تصویر، نسخه بهینه‌شده آن با استفاده از قابلیت موجود در `XController` ایجاد می‌شود.

### ۶.۴. مهاجرت محصولات



```bash
php artisan xshift product http://wp.test/
```

این دستور محصولات WooCommerce را از مسیر `/products` دریافت می‌کند.

اطلاعاتی که در کد فعلی منتقل می‌شوند:

- شناسه محصول
- نام
- نامک
- توضیحات کامل
- توضیحات کوتاه
- دسته‌بندی‌های مرتبط
- SKU، در صورت وجود
- تعداد موجودی، در صورت وجود
- قیمت، در صورت وجود
- وضعیت موجودی
- تصاویر محصول
- تاریخ ایجاد محصول

وضعیت موجودی محصولات مطابق جدول زیر نگاشت می‌شود:

| مقدار در WooCommerce | مقدار در xShop |
| --- | --- |
| `instock` | `IN_STOCK` |
| `onbackorder` | `BACK_ORDER` |
| `outofstock` | `OUT_STOCK` |

در صورت وجود چند تصویر برای یک محصول، تصاویر دریافت‌شده به مجموعه رسانه‌های همان محصول اضافه می‌شوند.

### ۶.۵. ترتیب پیشنهادی اجرای دستورات

برای مهاجرت کامل محتوای پشتیبانی‌شده، ترتیب زیر پیشنهاد می‌شود:



```bash
php artisan xshift group http://wp.test/
php artisan xshift category http://wp.test/
php artisan xshift post http://wp.test/
php artisan xshift product http://wp.test/
```

ابتدا گروه‌ها و دسته‌بندی‌ها منتقل می‌شوند تا هنگام انتقال نوشته‌ها و محصولات، اطلاعات ارتباطی موردنیاز در مقصد موجود باشد.

هرچند کد فعلی در عملیات نوشته‌ها و محصولات مستقیماً به وجود دسته‌بندی‌ها و گروه‌ها وابسته است، ترتیب بالا احتمال بروز خطاهای مرتبط با کلیدهای خارجی را کاهش می‌دهد.

**مهم:** در نسخه فعلی، پیش از اجرای عملیات نوشته‌ها و محصولات، بررسی صریح وجود شناسه‌های گروه و دسته‌بندی انجام نمی‌شود. بنابراین باید مطمئن شوید شناسه‌های دریافت‌شده از وردپرس با ساختار داده‌های مقصد سازگار هستند.

## ۷. معرفی عملیات مهاجرت

| عملیات | توضیح | خالی بودن جدول مقصد |
| --- | --- | --- |
| `group` | انتقال گروه‌های محتوا | الزامی |
| `category` | انتقال دسته‌بندی محصولات | الزامی |
| `post` | انتقال نوشته‌ها | الزامی |
| `product` | انتقال محصولات | الزامی |
| `clear` | پاک‌سازی تعدادی از جداول و داده‌ها | نیازمند تأیید کاربر |

برای عملیات `group`، `category`، `post` و `product`، اگر جدول مدل مربوطه از قبل دارای رکورد باشد، دستور با پیام خطا متوقف می‌شود.

برای مثال:



```text
The table must be empty to migrate
```

در این شرایط باید وضعیت داده‌های مقصد را بررسی کنید. اگر قصد شروع مهاجرت از ابتدا را دارید، می‌توانید پس از تهیه نسخه پشتیبان، عملیات پاک‌سازی را بررسی کنید.

توجه داشته باشید که خالی بودن جدول اصلی لزوماً به معنای خالی بودن جداول واسط، فایل‌های رسانه‌ای یا سایر داده‌های مرتبط نیست.

## ۸. پاک‌سازی اطلاعات موجود

برای پاک‌سازی داده‌های مشخص‌شده در دستور مهاجرت، از فرمان زیر استفاده می‌شود:



```bash
php artisan xshift clear
```

این عملیات در محیط `production` مجاز نیست و در محیط‌های دیگر، پیش از اجرا، تأیید کاربر را درخواست می‌کند.

نمونه پیام تأیید:



```text
Are you sure you want to clear all data?
```

در صورت تأیید، عملیات پاک‌سازی انجام می‌شود.

### ۸.۱. اطلاعاتی که پاک می‌شوند

طبق کد فعلی، جداول و مدل‌های زیر تحت تأثیر قرار می‌گیرند:

- جدول واسط `category_product`
- جدول واسط `group_post`
- `Category`
- `Group`
- `Post`
- `Creator`
- `Invoice`
- `Order`
- `Product`

جداول واسط با `TRUNCATE` پاک می‌شوند و مدل‌ها نیز با استفاده از `truncate()` پاک‌سازی می‌شوند.

### ۸.۲. هشدار مهم درباره عملیات clear

::: warning
**این دستور برای پاک‌سازی انتخابی یا بی‌خطر طراحی نشده است.**

- اطلاعات موجود در جداول نام‌برده حذف می‌شوند.
- اطلاعات سفارش‌ها و فاکتورها نیز در فهرست پاک‌سازی قرار دارند.
- پاک‌سازی ممکن است روی روابط و یکپارچگی داده‌ها تأثیر بگذارد.
- جداول واسط دیگری که در کد مشخص نشده‌اند، لزوماً پاک نمی‌شوند.
- فایل‌های رسانه‌ای و پوشه‌های ذخیره‌سازی در عملیات `clear` به‌صورت عمومی پاک نمی‌شوند.
- مدل `Redirect` نیز در این عملیات پاک نمی‌شود؛ بنابراین ریدایرکت‌های قبلی ممکن است باقی بمانند.
پیش از اجرای این دستور، از پایگاه داده نسخه پشتیبان بگیرید و مطمئن شوید حذف داده‌ها مورد تأیید است.

همچنین، در کد فعلی دستور `DB::statement('SET FOREIGN_KEY_CHECKS=0')` پیش از بررسی عملیات اجرا می‌شود و بازگرداندن این تنظیم به مقدار اولیه در پایان فرمان صریحاً انجام نشده است. رفتار آن را در محیط و نسخه پایگاه داده خود بررسی کنید.
:::

## ۹. انتقال تصاویر و فایل‌های رسانه‌ای

تصاویر از طریق URL موجود در پاسخ API دریافت می‌شوند. برای دانلود فایل‌ها از کتابخانه Guzzle استفاده شده است.

در پیاده‌سازی فعلی:

- حداکثر زمان انتظار درخواست دانلود ۳۰ ثانیه است.
- پاسخ‌هایی غیر از HTTP 200 به‌عنوان شکست دانلود در نظر گرفته می‌شوند.
- فایل‌ها به‌صورت جریانی دریافت و در فایل موقت ذخیره می‌شوند.
- تصاویر دسته‌بندی‌ها در پوشه اختصاصی خود ذخیره و بهینه می‌شوند.
- تصاویر نوشته‌ها و محصولات از طریق قابلیت Media Library به مجموعه رسانه‌های مربوطه اضافه می‌شوند.

مسیر ذخیره تصاویر دسته‌بندی‌ها:



```text
storage/app/public/categories/
```

### نکات مهم درباره تصاویر

- حجم تصاویر ممکن است مدت مهاجرت را به‌طور قابل توجهی افزایش دهد.
- اگر سرور مبدأ تصاویر را با محدودیت دسترسی ارائه کند، دانلود ممکن است شکست بخورد.
- در صورت بروز خطای دانلود، اطلاعات خطا در کد فعلی به‌صورت کامل و ساختاریافته ثبت نمی‌شود.
- مدیریت فایل‌های موقت و پاک‌سازی آن‌ها در تمام مسیرهای اجرای کد به‌صورت صریح تضمین نشده است.
- برای محصولات و نوشته‌ها، نام و نحوه سازمان‌دهی نهایی فایل‌ها به تنظیمات Media Library پروژه وابسته است.

پس از مهاجرت، تصاویر دسته‌بندی‌ها، تصاویر شاخص نوشته‌ها و گالری محصولات را در سایت مقصد بررسی کنید.

## ۱۰. مدیریت ریدایرکت‌ها

برای جلوگیری از ایجاد لینک‌های شکسته، کد مهاجرت آدرس قدیمی هر محتوا را با آدرس جدید آن مقایسه می‌کند.

اگر مسیر URL قدیمی و جدید متفاوت باشند، یک رکورد در مدل `Redirect` ایجاد می‌شود.

اطلاعات ذخیره‌شده شامل موارد زیر است:

- `source`: مسیر قدیمی
- `destination`: مسیر جدید
- `status`: مقدار `1`
- `expire`: تاریخ انقضا، ۱۸۰ روز پس از زمان اجرای عملیات

برای مقایسه مسیرها، بخش Path آدرس استخراج می‌شود و تفاوت دامنه یا پارامترهای Query String در این مقایسه لحاظ نمی‌شود.

برای مثال، اگر آدرس قدیمی چنین باشد:



```text
https://wp.example.com/old-post/
```

و آدرس جدید به شکل زیر باشد:



```text
https://shop.example.com/blog/new-post
```

مسیرها متفاوت هستند و رکورد ریدایرکت ایجاد می‌شود.

### نکات مربوط به ریدایرکت‌ها

- فقط تفاوت مسیر بررسی می‌شود؛ تغییر دامنه به‌تنهایی باعث ایجاد ریدایرکت نخواهد شد.
- مقدار `status` در کد روی `1` قرار می‌گیرد؛ نوع HTTP ریدایرکت باید از منطق مدل یا سیستم مدیریت ریدایرکت مشخص شود.
- تاریخ انقضا با استفاده از قالب `y-m-d` تولید می‌شود که سال را دو رقمی ذخیره می‌کند. اگر ستون مقصد به سال چهاررقمی نیاز دارد، باید این قسمت اصلاح شود.
- اجرای مجدد مهاجرت بدون پاک‌سازی ریدایرکت‌های قبلی ممکن است رکوردهای تکراری ایجاد کند.
- باید بررسی شود که سیستم مقصد، مسیرهای ذخیره‌شده در `Redirect` را به شکل مورد انتظار پردازش می‌کند.

## ۱۱. مدت‌زمان اجرای مهاجرت

مدت اجرای مهاجرت به عوامل مختلفی وابسته است:

- تعداد نوشته‌ها و محصولات
- تعداد دسته‌بندی‌ها و گروه‌ها
- تعداد تصاویر
- حجم فایل‌های رسانه‌ای
- سرعت پاسخ‌گویی سایت مبدأ
- سرعت اینترنت بین مبدأ و مقصد
- منابع سخت‌افزاری سرور مقصد
- زمان پردازش تصاویر

در پروژه‌های کوچک، مهاجرت ممکن است چند دقیقه طول بکشد؛ در سایت‌های بزرگ و دارای تصاویر فراوان، این فرآیند ممکن است چند ساعت زمان ببرد.

در طول اجرا، ترمینال را تا پایان عملیات باز نگه دارید و خروجی خطاها را بررسی کنید.

## ۱۲. خطاهای رایج و راه‌حل‌ها

### ۱۲.۱. خطای ضروری بودن URL

اگر دستور مهاجرت بدون آدرس وردپرس اجرا شود، پیام زیر نمایش داده می‌شود:



```text
url is necessary to migrate
```

راه‌حل:

آدرس سایت مبدأ را به دستور اضافه کنید:



```bash
php artisan xshift post https://wp.example.com/
```

### ۱۲.۲. خطای پر بودن جدول مقصد

اگر جدول مقصد دارای اطلاعات باشد، پیام زیر نمایش داده می‌شود:



```text
The table must be empty to migrate
```

راه‌حل:

- ابتدا اطلاعات موجود را بررسی کنید.
- در صورت نیاز، نسخه پشتیبان تهیه کنید.
- فقط در محیط مناسب و با تأیید حذف داده‌ها، عملیات پاک‌سازی را انجام دهید.

### ۱۲.۳. دریافت پاسخ نامعتبر از API

اگر مسیر API اشتباه باشد، افزونه فعال نباشد یا سایت مبدأ در دسترس نباشد، دریافت اطلاعات با مشکل مواجه می‌شود.

برای بررسی اولیه، URL متناظر با عملیات را در مرورگر یا با `curl` بررسی کنید:

bash

```
curl -i https://wp.example.com/wp-json/xshift/v1/posts
```

پاسخ باید از نظر HTTP و ساختار JSON معتبر باشد.

کد فعلی برای درخواست اصلی API مدیریت خطا و اعتبارسنجی ساختار JSON را به‌صورت کامل انجام نمی‌دهد؛ بنابراین ممکن است برخی خطاها به‌جای نمایش پیام مشخص، باعث شکست عملیات شوند.

### ۱۲.۴. خطای دانلود تصاویر

اگر تصویر دریافت نشود، موارد زیر را بررسی کنید:

- دسترسی سرور مقصد به URL تصویر
- معتبر بودن URL
- وضعیت پاسخ HTTP
- محدودیت‌های شبکه و فایروال
- فضای دیسک مقصد
- دسترسی نوشتن روی پوشه‌های ذخیره‌سازی

### ۱۲.۵. خطای مربوط به کاربر

نوشته‌ها و محصولات با شناسه اولین کاربر موجود در سیستم ثبت می‌شوند. اگر هیچ کاربری در جدول `users` وجود نداشته باشد، عملیات ممکن است با خطا مواجه شود.

راه‌حل:

پیش از مهاجرت، وجود حداقل یک کاربر معتبر را بررسی کنید.

### ۱۲.۶. خطای شناسه دسته‌بندی یا گروه

کد فعلی شناسه‌های دریافتی از وردپرس را برای ارتباط نوشته‌ها و محصولات با گروه‌ها و دسته‌بندی‌ها استفاده می‌کند.

اگر شناسه‌های مقصد موجود نباشند یا با داده‌های مبدأ تطابق نداشته باشند، احتمال بروز خطا یا ایجاد ارتباط نادرست وجود دارد.

راه‌حل:

ابتدا گروه‌ها و دسته‌بندی‌ها را منتقل کنید و سپس نوشته‌ها و محصولات را مهاجرت دهید.

### ۱۲.۷. خطاهای مربوط به نسخه PHP یا پایگاه داده

در صورت بروز خطاهای اجرایی، نسخه PHP، نسخه MySQL یا MariaDB، تنظیمات Laravel و وابستگی‌های پروژه را بررسی کنید.

همچنین مطمئن شوید ساختار ستون‌ها و روابط پایگاه داده با مدل‌های فعلی xShop سازگار است.

## ۱۳. نکات مهم و محدودیت‌ها

موارد زیر به پیاده‌سازی فعلی مربوط هستند و باید پیش از مهاجرت یک سایت واقعی در نظر گرفته شوند.

### ۱۳.۱. نبود تراکنش سراسری

عملیات مهاجرت در یک تراکنش واحد پایگاه داده اجرا نمی‌شود. اگر عملیات در میانه راه شکست بخورد، ممکن است بخشی از اطلاعات قبلاً ثبت شده باشد.

از آنجا که اجرای مجدد هر عملیات در صورت وجود رکورد در جدول اصلی متوقف می‌شود، ادامه مهاجرت پس از شکست ممکن است به پاک‌سازی کنترل‌شده یا اصلاح دستی داده‌ها نیاز داشته باشد.

### ۱۳.۲. احتمال برخورد شناسه‌ها

شناسه رکوردهای مبدأ مستقیماً در مدل‌های مقصد استفاده می‌شوند.

اگر شناسه‌ای در پایگاه داده مقصد از قبل استفاده شده باشد، ممکن است خطای تکراری بودن کلید اصلی رخ دهد یا روابط داده‌ها دچار مشکل شوند.

### ۱۳.۳. انتقال ناقص ویژگی‌های محصولات

در کد فعلی انتقال ویژگی‌های پیشرفته WooCommerce، متغیرها و گونه‌های محصول (Variations)، تخفیف‌ها، مالیات، کوپن‌ها، سفارش‌ها و تاریخچه تراکنش‌ها پیاده‌سازی نشده است.

همچنین کد انتقال اطلاعات اضافی محصول به‌صورت صریح در مرحله توسعه قرار دارد.

### ۱۳.۴. وضعیت نوشته‌ها و محصولات

وضعیت نوشته‌ها و محصولات در کد فعلی به مقدار `1` تنظیم می‌شود. این مقدار لزوماً وضعیت اصلی محتوا در وردپرس را بازنمایی نمی‌کند.

### ۱۳.۵. وابستگی به ساختار داده‌های API

کد انتظار دارد برخی فیلدها، از جمله شناسه دسته‌بندی‌های مرتبط، در پاسخ API موجود باشند. نبودن آرایه‌ها یا خالی بودن آن‌ها می‌تواند موجب خطا شود.

### ۱۳.۶. ثبت خطا و گزارش پیشرفت

پیاده‌سازی فعلی گزارش جامعی از تعداد رکوردهای موفق، ناموفق و ردشده ارائه نمی‌کند. همچنین مدیریت خطا برای همه درخواست‌ها و عملیات پایگاه داده یکسان نیست.

برای مهاجرت‌های بزرگ، افزودن Logging، گزارش پیشرفت و امکان ادامه عملیات از نقطه شکست پیشنهاد می‌شود.

### ۱۳.۷. ملاحظات امنیتی

- از HTTPS برای اتصال به سایت مبدأ استفاده کنید.
- API مبدأ را در برابر دسترسی غیرمجاز محافظت کنید.
- دسترسی اجرای فرمان‌های Artisan را محدود کنید.
- از اجرای `clear` روی داده‌های عملیاتی بدون نسخه پشتیبان خودداری کنید.
- برای دانلود فایل‌ها، دامنه‌های مجاز را محدود کنید؛ دریافت URLهای دلخواه از API می‌تواند خطر دسترسی ناخواسته به منابع داخلی سرور را ایجاد کند.
- برای فایل‌های حجیم، محدودیت حافظه، زمان اجرا و فضای دیسک را بررسی کنید.

## ۱۵. جمع‌بندی

برای مهاجرت اطلاعات از WordPress و WooCommerce به xShop، ابتدا افزونه `xshift` را روی سایت مبدأ نصب و فعال کنید. سپس در پوشه پروژه xShop، عملیات مهاجرت را به‌ترتیب گروه‌ها، دسته‌بندی‌ها، نوشته‌ها و محصولات اجرا کنید.

نمونه دستورات:



```bash
php artisan xshift group https://wp.example.com/
php artisan xshift category https://wp.example.com/
php artisan xshift post https://wp.example.com/
php artisan xshift product https://wp.example.com/
```

اگر جدول‌های مقصد از قبل اطلاعات داشته باشند، عملیات متناظر متوقف می‌شود. در این شرایط، پیش از هرگونه پاک‌سازی، نسخه پشتیبان تهیه کنید و اثر عملیات `clear` بر داده‌های موجود را بررسی کنید.

در نهایت، انتقال موفق داده‌ها را صرفاً بر اساس پایان یافتن دستورات ارزیابی نکنید؛ تصاویر، ارتباط رکوردها، ریدایرکت‌ها و صحت اطلاعات فروشگاه را نیز در محیط مقصد بررسی کنید.
