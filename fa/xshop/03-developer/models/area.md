# Area

Model reference · `App\Models\Area`

### 1. Model

مدل `Area` یکی از اجزای اصلی موتور مدیریت Theme در سیستم است. این مدل مشخص می‌کند هر نوع صفحه یا محیط سایت چه ساختاری دارد، چه `segment`هایی می‌تواند استفاده کند و چه تعداد `theme part` در آن قابل تعریف است.

در این معماری، ظاهر سایت صرفاً با یک قالب یکپارچه برای تمام صفحات تعیین نمی‌شود. هر محیط می‌تواند ساختار و اجزای مخصوص خودش را داشته باشد؛ برای مثال، صفحه محصول، فهرست محصولات، صفحه مقاله، سبد خرید و صفحه تماس با ما هرکدام یک `Area` مستقل دارند.

همچنین بعضی `Area`ها برای صفحات معمولی نیستند و کاربرد ویژه‌ای دارند؛ مانند `defaultHeader`، `defaultFooter`، `preloader` و `floats`.

برای درک این مدل، باید سه مفهوم اصلی را از هم جدا کرد:

- **Area:** محیطی که ساختار قابل تنظیم یک صفحه یا بخش از سایت را مشخص می‌کند؛ مانند `product` یا `products-list`.
- **segment:** نوع یا جایگاه یک بخش از صفحه که می‌تواند در آن محتوا یا ساختار مشخصی قرار بگیرد؛ مانند `header`، `footer`، `slider` یا `product_grid`. segmentهای مربوط به این سیستم در مسیر `resources/views/segments/` قرار دارند.
- **theme part:** یک جزء قابل استفاده از Theme که به یک segment تعلق دارد و می‌تواند در یک Area قرار بگیرد. ارتباط Area با theme partها از طریق مدل `Part` مدیریت می‌شود.

بنابراین، `Area` مشخص می‌کند چه چیزهایی مجازند در یک محیط قرار بگیرند؛ `segment` نوع جایگاه را مشخص می‌کند و `theme part` پیاده‌سازی مشخصی از آن بخش است.

### 3. Extra description of table fields

**`areas.name`**

نام یکتای محیط را مشخص می‌کند. این نام برای شناسایی Area در سیستم استفاده می‌شود و از آنجا که دارای محدودیت `UNIQUE` است، دو Area نمی‌توانند نام یکسان داشته باشند.

نمونه‌هایی از نام محیط‌ها:

- `index` — صفحه اصلی
- `product` — صفحه جزئیات محصول
- `products-list` — صفحه فهرست محصولات
- `post` — صفحه جزئیات مقاله
- `posts-list` — صفحه فهرست مقالات
- `contact-us` — صفحه تماس با ما
- `under-construction` — صفحه در دست ساخت
- `product-grid` — محیط مخصوص نمایش محصولات در قالب Grid
- `defaultHeader` و `defaultFooter` — محیط‌های مربوط به بخش‌های پیش‌فرض Header و Footer
- `preloader` — محیط مربوط به Preloader
- `floats` — محیط مربوط به اجزای شناور سایت

**`areas.max`**

حداکثر تعداد theme partهایی را مشخص می‌کند که می‌توانند در یک Area قرار بگیرند.

این مقدار برای همه محیط‌ها یکسان نیست؛ چون نیاز هر محیط متفاوت است. برای مثال، در Seeder مقدار `max` برای `preloader` برابر `1`، برای `product-grid` برابر `1` و برای صفحه اصلی (`index`) برابر `10` تعریف شده است.

در محیطی مانند Footer نیز می‌توان تعداد اجزای قابل استفاده را محدود کرد تا ساختار آن از تعداد تعیین‌شده فراتر نرود.

**`areas.icon`**

نام آیکون مورد استفاده در پنل مدیریت را نگهداری می‌کند. این آیکون‌ها از مجموعه Remix Icon انتخاب می‌شوند و برای شناسایی سریع محیط‌ها در رابط کاربری پنل کاربرد دارند.

برای مثال، Seeder برای محیط `product-grid` از `ri-layout-grid-line` و برای `preloader` از `ri-loader-2-line` استفاده می‌کند.

**`areas.valid_segments`**

فهرستی از segmentهایی را نگهداری می‌کند که استفاده از آن‌ها در این Area مجاز است. این مقدار به‌صورت JSON ذخیره می‌شود و امکان تعریف ساختار متفاوت برای محیط‌های مختلف را فراهم می‌کند.

برای مثال، در Seeder محیط `product` می‌تواند از segmentهایی مانند `header`، `footer`، `product`، `comments`، `ads` و `attachments` استفاده کند؛ درحالی‌که محیط `product-grid` فقط segment مربوط به `product_grid` را می‌پذیرد.

این محدودیت به این معناست که هر Area مجموعه مشخصی از جایگاه‌های قابل استفاده دارد و نمی‌توان بدون در نظر گرفتن تعریف آن، هر segment دلخواهی را در آن قرار داد.

فهرست کلی segmentهای شناخته‌شده در مدل تعریف شده است؛ اما فهرست segmentهای مجاز هر Area به‌صورت مستقل در `valid_segments` ذخیره می‌شود. در نتیجه، «شناخته‌شده بودن یک segment در سیستم» با «مجاز بودن آن در یک Area خاص» یکسان نیست.

**`areas.preview`**

نام  route مورد استفاده برای پیش‌نمایش محیط را نگهداری می‌کند. در محیط‌هایی که پیش‌نمایش برای آن‌ها تعریف شده است، این فیلد مشخص می‌کند کدام route باید برای نمایش پیش‌نمایش استفاده شود.

برای مثال، Seeder برای محیط `index` مقدار `client.welcome`، برای `products-list` مقدار `client.products` و برای `product-grid` مقدار `null` در نظر گرفته است.

بنابراین، وجود پیش‌نمایش برای تمام Areaها الزامی نیست.

**`areas.use_default`**

مشخص می‌کند محیط از ساختارهای پیش‌فرض `defaultHeader` و `defaultFooter` استفاده می‌کند یا Header و Footer اختصاصی خودش را دارد.

این قابلیت برای تفکیک محیط‌هایی که باید از اجزای عمومی سایت استفاده کنند از محیط‌هایی که ساختار اختصاصی دارند در نظر گرفته شده است.

**`areas.sort`**

ترتیب نمایش محیط‌ها را مشخص می‌کند. این فیلد برای مرتب‌سازی Areaها در رابط کاربری یا بخش‌هایی از سیستم که ترتیب محیط‌ها اهمیت دارد استفاده می‌شود.

مقدار پیش‌فرض آن `0` است و می‌توان برای محیط‌های خاص، مقدار متفاوتی تعریف کرد؛ برای مثال، در Seeder مقدار `97` برای `index` و `99` برای `defaultHeader` در نظر گرفته شده است. ولی هنگام نمایش اصلاح می‌شود تا با بقیه عناصر تداخل نداشته باشند.

### 4. Methods

**`getSegmentAttribute()`**

```php
public function getSegmentAttribute()
{
    return json_decode($this->valid_segments, true);
}
```

این Accessor مقدار JSON ذخیره‌شده در `valid_segments` را به یک آرایه PHP تبدیل می‌کند تا در کد بتوان با فهرست segmentهای مجاز کار کرد.

برای مثال، اگر مقدار `valid_segments` برابر با این JSON باشد:

```json
["header", "footer", "ads"]
```

دسترسی به ویژگی `segment`، آرایه‌ای معادل زیر را برمی‌گرداند:

```php
['header', 'footer', 'ads']
```

در نتیجه، به‌جای پردازش مستقیم رشته JSON، می‌توان از مقدار تبدیل‌شده در منطق برنامه استفاده کرد.

**`getRouteKeyName()`**


مشخص می‌کند Laravel هنگام استفاده از Route Model Binding برای این مدل، به‌جای فیلد پیش‌فرض `id` از فیلد `name` استفاده کند.

برای مثال، در صورتی که Route Model Binding برای این مدل تعریف شده باشد، می‌توان یک Area را با نامی مانند `product` شناسایی کرد. این رفتار با یکتا بودن `areas.name` در دیتابیس سازگار است.

**`parts()`**


رابطه‌ی `hasMany` با مدل `Part` را تعریف می‌کند. این رابطه تمام theme partهای مرتبط با یک Area را در دسترس قرار می‌دهد.

این رابطه بخش مهمی از ساختار Theme است؛ چون یک Area می‌تواند چند theme part داشته باشد، البته تعداد آن‌ها تابع محدودیت `max` و منطق مدیریت سیستم است.

برای مثال، از این رابطه می‌توان برای دریافت theme partهای محیط صفحه اصلی یا محیط جزئیات محصول استفاده کرد.

**`defPart()`**

```php
public function defPart()
{
    $p = $this->parts()->first();

    return 'segments.' . $p->segment . '.' . $p->part . '.' . $p->part;
}
```

این متد یک مسیر View برای استفاده مستقیم از theme part مربوط به Area برمی‌گرداند. کاربرد اصلی آن، فراهم کردن یک مسیر کوتاه و قابل استفاده برای درج یک جزء از Theme در بخش‌های دیگر قالب است؛ بدون اینکه لازم باشد مسیر View آن جزء در تمام نقاط برنامه به‌صورت دستی نوشته شود.

برای درک کاربرد آن، محیط `product-grid` را در نظر بگیرید. این محیط برای نمایش یک محصول در قالب Grid در نظر گرفته شده است؛ یعنی یک ساختار قابل استفاده مجدد برای نمایش محصول، نه لزوماً یک صفحه مستقل با Header و Footer کامل.

در نمونه زیر، ابتدا محصولات مرتبط با محصول فعلی دریافت می‌شوند و سپس برای هر محصول، View مربوط به محیط `product-grid` درج می‌شود:

```php
@foreach(\App\Models\Product::whereIn('id', $product->relatedProduct())->get() as $p)
    <div class="item">
        @include(
            \App\Models\Area::where('name', 'product-grid')->first()->defPart(),
            ['product' => $p]
        )
    </div>
@endforeach
```

در این مثال، کد مستقیماً مسیر فایل یک قالب مشخص را نمی‌نویسد. به‌جای آن، Area با نام `product-grid` پیدا می‌شود و `defPart()` مسیر View مربوط به اولین `Part` آن را برمی‌گرداند. سپس همان View با متغیر `product` برای هر محصول درج می‌شود.

مزیت این روش آن است که محل استفاده از محصول در قالب، به مسیر ثابت و دستی یک فایل وابسته نیست؛ بلکه از تعریف Theme در سیستم پیروی می‌کند. در نتیجه، اگر theme part مربوط به این Area تغییر کند، کد استفاده‌کننده همچنان از مسیر به‌دست‌آمده از خود Area استفاده خواهد کرد.

نکته مهم این است که `defPart()` فقط اولین `Part` مرتبط را انتخاب می‌کند؛ خودش همه theme partهای محیط را رندر نمی‌کند و منطق انتخاب اولین مورد نیز در همین متد مشخص شده است. همچنین مسیر نهایی View از مقادیر `segment` و `part` همان رکورد ساخته می‌شود.
