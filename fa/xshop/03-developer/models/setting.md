# Setting

مدل `Setting` مسئول مدیریت تنظیمات سیستم است. این مدل علاوه بر نگهداری مقادیر تنظیمات، اطلاعات لازم برای تعریف نوع ورودی، عنوان، نحوه‌ی نمایش و اعتبارسنجی آن‌ها را نیز در اختیار سیستم قرار می‌دهد.

برخلاف یک ساختار ساده‌ی کلید و مقدار، هر تنظیم می‌تواند نوع داده، عنوان، بخش، وضعیت فعال بودن، اطلاعات تکمیلی و تنظیمات نمایشی مخصوص خود را داشته باشد. به کمک این ساختار، تنظیمات جدید را می‌توان بدون نیاز به طراحی یک صفحه‌ی اختصاصی برای هر مورد، به رابط مدیریت اضافه کرد.

یکی از کاربردهای مهم این معماری، امکان تعریف تنظیمات موردنیاز Theme Partها است؛ به‌طوری‌که با اضافه شدن یک بخش به قالب، تنظیمات موردنیاز آن نیز ایجاد می‌شوند.

## ساختار داده
| فیلد | نوع                    | Nullable | توضیحات |
|---|------------------------|---|---|
| `id` | BIGINT UNSIGNED        | خیر | شناسه‌ی یکتای تنظیم |
| `section` | VARCHAR(255)           | خیر | بخشی که تنظیم به آن تعلق دارد؛ برای مثال `General`، `SEO`، `Media`، `SMS` یا `Theme` |
| `type` | ENUM(توضیحات در ادامه) | خیر | نوع تنظیم که رفتار ورودی و شیوه‌ی دریافت مقدار آن را مشخص می‌کند |
| `title` | VARCHAR(255)           | خیر | عنوان قابل نمایش تنظیم در پنل مدیریت |
| `active` | TINYINT(1)             | خیر | وضعیت فعال یا غیرفعال بودن تنظیم |
| `key` | VARCHAR(255)، unique   | خیر | کلید یکتای تنظیم که برای دسترسی به مقدار آن استفاده می‌شود |
| `value` | LONGTEXT               | بله | مقدار تنظیم که قابلیت ترجمه دارد |
| `raw` | LONGTEXT               | بله | مقدار خام و ترجمه‌نشده‌ی تنظیم |
| `ltr` | TINYINT(1)             | خیر | مشخص می‌کند ورودی باید به‌صورت چپ‌به‌راست نمایش داده شود یا خیر |
| `is_basic` | TINYINT(1)             | خیر | مشخص می‌کند مقدار تنظیم باید از قواعد اعتبارسنجی تنظیمات پایه پیروی کند یا خیر |
| `size` | TINYINT                | خیر | اندازه‌ی ستون تنظیم در رابط کاربری مبتنی بر Grid بوت‌استرپ، از ۱ تا ۱۲ |
| `data` | LONGTEXT، JSON         | بله | اطلاعات تکمیلی تنظیم در قالب JSON؛ کاربرد آن به نوع تنظیم و مصرف‌کننده‌ی آن بستگی دارد |
| `created_at` | TIMESTAMP              | بله | زمان ایجاد تنظیم |
| `updated_at` | TIMESTAMP              | بله | زمان آخرین به‌روزرسانی تنظیم |
فیلد `key` دارای محدودیت یکتایی در دیتابیس است؛ بنابراین دو تنظیم نمی‌توانند کلید یکسان داشته باشند، حتی اگر در بخش‌های متفاوتی قرار گرفته باشند.

## بخش‌بندی تنظیمات

فیلد `section` مشخص می‌کند تنظیمات در کدام بخش از پنل مدیریت قرار بگیرند. بخش‌های پیش‌فرض سیستم عبارت‌اند از:

### General

تنظیمات عمومی سایت؛ مانند نام سایت، عنوان، کلمات کلیدی و اطلاعات شبکه‌های اجتماعی.

### SMS

تنظیمات مربوط به پیامک‌ها، از جمله متن پیام‌های احراز هویت. متن پیام می‌تواند مستقیماً تعریف شود یا از قالب‌های پیامکی استفاده کند.

### SEO

تنظیمات مربوط به سئو و رفتارهای مرتبط با آن؛ مانند تنظیمات نقشه‌ی سایت چندزبانه، نقشه‌ی سایت دسته‌بندی‌ها و استفاده از آدرس Canonical برای خود محصولات و نوشته‌ها.

### Media

تنظیمات مربوط به مدیریت رسانه‌ها؛ مانند ابعاد تصاویر بندانگشتی، فرمت خروجی تصویر، بهینه‌سازی تصاویر، واترمارک خودکار و لوگوی سایت.

### Theme

تنظیمات مربوط به قالب و اجزای آن. این بخش می‌تواند علاوه بر تنظیمات عمومی قالب، تنظیمات موردنیاز Theme Partهای ثبت‌شده را نیز در خود جای دهد.

بخش‌های فوق، بخش‌بندی پیش‌فرض سیستم هستند؛ ساختار مدل به این پنج مورد محدود نشده است.

## کلید و مقدار تنظیم

### `key`

کلید اصلی دسترسی به تنظیم است. برای مثال، تنظیمی با کلید `cache_number` را می‌توان با استفاده از helper مربوط به تنظیمات دریافت کرد:

`getSetting('cache_number')`

این کلید، شناسه‌ی منطقی تنظیم در سطح برنامه است و برای دسترسی به آن لازم نیست شناسه‌ی عددی رکورد دیتابیس را بدانیم.

### `value`

مقدار تنظیم است و در مدل به‌عنوان فیلد قابل ترجمه تعریف شده است:

`public $translatable = ['value'];`

در نتیجه، مقدار این فیلد می‌تواند متناسب با زبان جاری برنامه متفاوت باشد. برای مثال، اگر تنظیمی حاوی یک متن قابل نمایش به کاربر باشد، مقدار آن می‌تواند ترجمه شود.

### `raw`

مقدار خام تنظیم را نگهداری می‌کند تا در مواقعی که مقدار بدون ترجمه لازم است، از آن استفاده شود.

برای مثال، فرض کنید مقدار یک تنظیم به شکل عددی یا رشته‌ای مانند `500x500` تعریف شده باشد. اگر مقدار `value` تحت تأثیر سازوکار ترجمه قرار بگیرد، ممکن است برای پردازش یا اعتبارسنجی، مقدار ترجمه‌نشده مناسب‌تر باشد.

وجود `raw` این امکان را فراهم می‌کند که بین مقدار قابل استفاده در زمینه‌ی ترجمه و مقدار خام موردنیاز پردازش تفاوت وجود داشته باشد.

## انواع تنظیمات (`type`)

فیلد `type` تعیین می‌کند هر تنظیم چه نوع ورودی‌ای داشته باشد و مقدار آن چگونه در اختیار مدیر قرار بگیرد. این فیلد از یک مجموعه‌ی مشخص از انواع پشتیبانی می‌کند که در `$settingTypes` مدل تعریف شده‌اند.

### ورودی‌های متنی و عمومی

| نوع | کاربرد |
|---|---|
| `TEXT` | دریافت متن معمولی تک‌خطی |
| `NUMBER` | دریافت مقدار عددی |
| `LONGTEXT` | دریافت متن چندخطی |
| `CODE` | دریافت کدهایی مانند اسکریپت Google Webmaster |
| `EDITOR` | دریافت متن با ویرایشگر CKEditor |
| `CHECKBOX` | ورودی روشن/خاموش یا Switch |
| `FILE` | بارگذاری فایل؛ برای فایل‌های مجاز و غیرحساس، نه فایل‌های اجرایی خطرناک مانند PHP |
| `COLOR` | انتخاب رنگ |
| `ICON` | انتخاب آیکون |

### انتخاب یک مقدار

| نوع | کاربرد |
|---|---|
| `CATEGORY` | انتخاب یک دسته‌بندی محصول |
| `GROUP` | انتخاب یک سرفصل نوشته |
| `CREATOR` | انتخاب یک سازنده یا مؤلف |
| `MENU` | انتخاب یک منوی موجود |
| `SELECT` | انتخاب یک مقدار از فهرست گزینه‌ها |

### ورودی‌های زمانی و مکانی

| نوع | کاربرد |
|---|---|
| `LOCATION` | انتخاب موقعیت جغرافیایی و دریافت اطلاعاتی مانند طول و عرض جغرافیایی |
| `DATE` | انتخاب تاریخ با Date Picker دوگانه‌ی شمسی و میلادی |
| `DATETIME` | انتخاب تاریخ و زمان با پشتیبانی از تقویم شمسی و میلادی |
| `TIME` | انتخاب زمان بدون تاریخ |

### انتخاب مجموعه‌ها

این انواع برای زمانی هستند که یک تنظیم به چند موجودیت یا چند مقدار نیاز دارد.

| نوع | کاربرد |
|---|---|
| `CATEGORY_SET` | انتخاب چند دسته‌بندی محصول |
| `GROUP_SET` | انتخاب چند سرفصل نوشته |
| `CREATOR_SET` | انتخاب چند سازنده یا مؤلف |
| `SETS` | انتخاب چند مقدار از مجموعه‌ای از گزینه‌ها؛ مشابه مفهوم `SET` در MySQL |

### انواع مبتنی بر Query

| نوع | کاربرد |
|---|---|
| `PRODUCT_QUERY` | تعریف یک کوئری برای انتخاب محصولات بر اساس معیارهایی مانند دسته‌بندی، ترتیب و فیلترها |
| `POST_QUERY` | تعریف کوئری مشابه برای انتخاب نوشته‌ها |

این دو نوع با انتخاب یک محصول یا نوشته‌ی منفرد تفاوت دارند؛ هدف آن‌ها فراهم کردن امکان تعریف مجموعه‌ای از نتایج بر اساس معیارهای انتخاب است.

## تنظیمات پویا برای Theme Partها

یکی از کاربردهای مهم مدل `Setting`، فراهم کردن تنظیمات موردنیاز اجزای قالب است.

فرض کنید یک Theme Part برای نمایش فرم تماس با ما به قالب اضافه می‌شود. این بخش ممکن است به تنظیمات زیر نیاز داشته باشد:

- آدرس شرکت با نوع `LOCATION`
- رنگ فرم تماس با ما با نوع `COLOR`
- دسته‌بندی محصولات حامی شرکت با نوع `CATEGORY_SET`

در این معماری، تنظیمات موردنیاز Theme Part با اضافه شدن آن ایجاد می‌شوند و در بخش `Theme` در دسترس قرار می‌گیرند. به این ترتیب، توسعه‌دهنده‌ی Theme Part می‌تواند تنظیمات مرتبط با همان بخش را تعریف کند، بدون اینکه لازم باشد برای هر تنظیم یک صفحه‌ی مدیریتی اختصاصی طراحی شود.

چرخه‌ی عمر این تنظیمات نیز به Theme Part مربوط است: با حذف Theme Part، تنظیمات وابسته به آن حذف می‌شوند؛ صرفاً غیرفعال نمی‌شوند.

این ویژگی باعث می‌شود تنظیمات یک قالب به‌صورت متمرکز و متناسب با اجزای فعال آن مدیریت شوند. همچنین امکان تعریف تنظیمات متنوع برای اجزای مختلف قالب، بدون محدود شدن به مجموعه‌ای ثابت از تنظیمات از پیش تعیین‌شده، فراهم می‌شود.

## اعتبارسنجی تنظیمات پایه

فیلد `is_basic` برای مشخص کردن تنظیماتی در نظر گرفته شده است که مقدار آن‌ها باید از قواعد اعتبارسنجی مخصوص تنظیمات پایه پیروی کند.

برای مثال، تنظیم اندازه‌ی تصویر ممکن است به مقداری مانند `500x500` نیاز داشته باشد یا فرمت خروجی تصویر باید از میان مقادیر مجاز مانند `jpg` و `webp` انتخاب شود.

در این موارد، helper مربوط به `validateSettingRequest` برای بررسی مقدار ورودی استفاده می‌شود.

این سازوکار کمک می‌کند تنظیماتی که قالب یا بخش‌های دیگر سیستم به آن‌ها وابسته‌اند، پیش از ذخیره شدن از نظر قالب و مقادیر مجاز بررسی شوند.

## اطلاعات تکمیلی (`data`)

فیلد `data` برای ذخیره‌ی اطلاعات اضافی مرتبط با یک تنظیم استفاده می‌شود. این اطلاعات به‌صورت JSON نگهداری می‌شوند و می‌توانند بسته به نوع تنظیم یا بخشی که آن را مصرف می‌کند، کاربردهای متفاوتی داشته باشند.

چند نمونه از کاربردهای آن:

- نگهداری محدوده‌ی عددی مجاز، مانند `{"xmin":0,"xmax":9007199254740992}`
- نگهداری نام یک متغیر CSS، مانند `{"name":"login-bg-color-1"}`
- نگهداری فهرست گزینه‌های پیش‌فرض برای یک ورودی از نوع `SELECT`

در مثال مربوط به CSS، نام متغیر می‌تواند در بخش‌هایی از سیستم برای افزودن یا استفاده از متغیر CSS به کار برود.

بنابراین `data` با `value` تفاوت دارد: `value` مقدار اصلی تنظیم است، درحالی‌که `data` اطلاعات تکمیلی موردنیاز برای تفسیر، نمایش یا استفاده از آن تنظیم را نگهداری می‌کند.

## تنظیمات نمایشی

### `ltr`

این فیلد برای تنظیم جهت نمایش ورودی به‌صورت چپ‌به‌راست استفاده می‌شود. برای نمونه، URLها و کدها معمولاً باید با جهت `LTR` نمایش داده شوند تا خواندن و ویرایش آن‌ها در رابط فارسی راحت‌تر باشد.

### `size`

این فیلد اندازه‌ی تنظیم را در چیدمان رابط مدیریت مشخص می‌کند. مقدار آن بر اساس Grid دوازده‌ستونی بوت‌استرپ و در بازه‌ی ۱ تا ۱۲ تعیین می‌شود.

برای مثال، مقدار `12` به معنی اشغال تمام عرض سطر و مقدار `4` به معنی اشغال یک‌سوم عرض آن است.

### `active`

وضعیت فعال یا غیرفعال بودن تنظیم را مشخص می‌کند. مقدار پیش‌فرض آن `1` است.

این فیلد با `is_basic` متفاوت است: `active` به وضعیت تنظیم مربوط است، درحالی‌که `is_basic` برای مشخص کردن نیاز به اعتبارسنجی مخصوص تنظیمات پایه استفاده می‌شود.

## متدها

### `getData()`

محتوای فیلد `data` را با استفاده از `json_decode` به آرایه‌ی PHP تبدیل می‌کند:

`json_decode($this->data, true)`

این متد اطلاعات تکمیلی تنظیم را به شکل آرایه در اختیار مصرف‌کننده قرار می‌دهد.

## نکات فنی

- کلید `key` در دیتابیس یکتا است؛ بنابراین هنگام تعریف تنظیم جدید باید کلیدی انتخاب شود که قبلاً استفاده نشده باشد.
- فیلد `value` قابل ترجمه است، اما `raw` برای دسترسی به مقدار خام و ترجمه‌نشده در نظر گرفته شده است.
- مقدار `data` باید JSON معتبر باشد؛ این موضوع با محدودیت `CHECK (json_valid(data))` در دیتابیس کنترل می‌شود.
- انواع مجاز تنظیمات در `$settingTypes` تعریف شده‌اند. افزودن یک مقدار جدید به این فهرست به‌تنهایی تضمین نمی‌کند که تمام رفتارهای لازم برای ورودی، ذخیره‌سازی و اعتبارسنجی آن پیاده‌سازی شده باشند.
- تنظیمات پویا و وابسته به Theme Partها بخشی از چرخه‌ی عمر همان اجزا هستند؛ بنابراین حذف یک Theme Part می‌تواند به حذف تنظیمات مرتبط با آن منجر شود.
